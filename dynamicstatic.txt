===============================================================================
               CYBERNEXUS ARCHITECTURAL ANALYSIS: DYNAMIC vs STATIC
===============================================================================

This document breaks down which modules and features in the CyberNexus Cybersecurity 
Learning Platform are DYNAMIC versus STATIC, explaining the architectural "WHY" 
behind each design choice.

-------------------------------------------------------------------------------
1. DYNAMIC COMPONENTS (Real-Time Server Processing & Live State)
-------------------------------------------------------------------------------

[A] SOCKET.IO LIVE INTEL FEED & OPERATIVE BROADCASTS
    - Status: DYNAMIC
    - Why: Uses bidirectional Socket.io WebSocket connections. Messages, 
      SOC network alerts, and active operative node counts are dynamically 
      broadcasted in real time across all connected user sessions without page reloads.

[B] USER AUTHENTICATION & PROFILE SYSTEM (JWT, OAuth & MongoDB)
    - Status: DYNAMIC
    - Why: User sessions, profile details (Username, Age, Location, Gender), 
      and JWT authentication tokens are evaluated server-side. Profile updates 
      issue live API HTTP requests (PUT /api/auth/profile) that persist to MongoDB/memory.

[C] INTERACTIVE TERMINAL & SHELL EMULATOR
    - Status: DYNAMIC
    - Why: Parses input at runtime, maintains stateful directory tracking (CWD), 
      executes interactive commands (nmap, gobuster, hydra, cat, sqlmap, nc), and 
      evaluates flag submissions dynamically.

[D] CERTIFICATE GENERATION & VERIFICATION LEDGER
    - Status: DYNAMIC
    - Why: Certificate verification queries a live database route (/api/verify-certificate/:id), 
      validates cryptographic hashes dynamically, and renders personalized certificates with 
      unique timestamped QR codes and recipient credentials.

[E] GAMIFICATION, XP PROGRESSION & CTF VALIDATION ENGINE
    - Status: DYNAMIC
    - Why: Calculates XP gains, evaluates level-up thresholds, unlocks achievements, 
      and validates CTF flag submissions on-the-fly, updating student state instantly.

-------------------------------------------------------------------------------
2. STATIC COMPONENTS (Pre-compiled Assets & Structural References)
-------------------------------------------------------------------------------

[A] CURRICULUM SYLLABUS, LESSONS & LEARNING TRACKS
    - Status: STATIC
    - Why: Course structures, lesson markdown, and lab setup descriptions are 
      structured constants (ALL_LEARNING_PATHS, ALL_LESSONS). They provide a 
      consistent, standardized educational curriculum for all students.

[B] REFERENCE GUIDES & CHEAT SHEETS (file.txt, CYBER_NEXUS_FULL_GUIDE.md)
    - Status: STATIC
    - Why: Pre-configured reference documentation, Kali Linux command cheatsheets, 
      and level progression tables served directly as static files for instant 
      offline reference or download.

[C] NETWORK TOPOLOGY DIAGRAMS & CTF SCENARIO DEFINITIONS
    - Status: STATIC
    - Why: Network topology nodes, diagram connections (InteractiveDiagram.jsx), 
      and initial challenge specifications are fixed declarative structures so 
      every student encounters identical, repeatable simulation environments.

[D] UI REACT COMPONENT LAYOUTS & STYLING
    - Status: STATIC
    - Why: The single-page React frontend application layout, Tailwind CSS utility 
      styling, and navigation tabs are compiled static assets bundled by Vite for 
      ultra-fast client-side rendering.

===============================================================================
                         CYBERNEXUS ARCHITECTURE SUMMARY
===============================================================================
CyberNexus utilizes a Hybrid Architecture:
  - STATIC assets provide predictable, ultra-fast educational delivery and UI rendering.
  - DYNAMIC services handle real-time SOC simulation, operative chat, user authentication,
    live terminal commands, and cryptographic certificate verification.
